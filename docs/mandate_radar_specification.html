1. Executive Summary & Problem Landscape

Recurring payments pile up quietly over the years: subscriptions, premium apps used twice, trials that stealthily convert, and prices that creep up unnoticed. The problem statement "The Auto Debits Nobody Can Find" highlights a fundamental breakdown in modern consumer banking.

Why Current Banking Systems Fail

  • Machine Descriptors: Statements display cryptic strings like ACH*AMZN*PRM*99*BLR or BILLDESK*NFLX*MUM instead of human brand names.
  • Fragmented Mandate Hubs: Autopays are scattered across bank netbanking, UPI apps (GPay, PhonePe), and cards with zero unified dashboard.
  • Deliberate Friction ("Dark Patterns"): Merchants intentionally obscure cancellation paths and offer no incentive to explain how to stop charges.
  • Invisible Price Creeps: Mandates permit variable or upper-limit deductions; price bumps happen silently without requiring re-authentication.

Finatic's Dual Solution Matrix

  • On-Device Radar (Finatic App): Real-time SMS and statement ingestion, NLP regex entity parser, and instant Brutalist user dashboard.
  • Neo4j Mandate Knowledge Graph: Transforms isolated transaction strings into an interconnected network connecting bank accounts, raw descriptors, merchant corporate entities, payment rails, and cancellation DAGs.
  • The "Annual Bleed" Trigger: Aggregates recurring leakages into a stark yearly loss total (e.g., "₹58,400/year") to shatter consumer inertia.
  • Actionable Runbooks: Step-by-step kill-switches tailored to the specific payment mechanism, including merchant ghosting protocols.

4. Production Cypher Query Library for Trap Detection

These four native Cypher queries power the detection engine and serve as key exhibits during the sponsor evaluation:

Query 1: Silent Price Increase Detection

Detects consecutive debit events within an active mandate where the subsequent charge exceeds the prior charge without user notification:

MATCH (m:Mandate)-[:BILLED]->(t1:DebitEvent)-[:NEXT_CHARGE]->(t2:DebitEvent)
MATCH (m)-[:CHARGED_BY]->(merch:Merchant)
WHERE t2.amount > t1.amount
RETURN merch.name AS Service,
       m.rail AS PaymentRail,
       t1.amount AS PreviousCharge,
       t2.amount AS CurrentCharge,
       (t2.amount - t1.amount) AS StealthHikeAmount,
       round(((t2.amount - t1.amount) / t1.amount) * 100, 1) AS PercentageIncrease,
       t2.date AS EffectiveDate

Query 2: Free-Trial-to-Paid Ambush Detection

Identifies token authorizations (≤ ₹2) that quietly convert into high-dollar recurring charges within 32 days:

MATCH (m:Mandate)-[:BILLED]->(t0:DebitEvent)-[:NEXT_CHARGE]->(t1:DebitEvent)
MATCH (m)-[:CHARGED_BY]->(merch:Merchant)
WHERE t0.amount <= 2.0 
  AND t1.amount >= 149.0
  AND duration.inDays(date(t0.date), date(t1.date)).days <= 32
RETURN merch.name AS Service,
       t0.amount AS TrialAuthFee,
       t1.amount AS ConvertedPlanCharge,
       t1.date AS ConversionDate,
       "CRITICAL_TRIAL_CONVERSION" AS ThreatLevel

Query 3: Cross-Account Double Subscription Discovery

Detects cases where a single user is unwittingly paying for the same underlying service across two distinct accounts or rails:

MATCH (u:User)-[:OWNS]->(acc1:Account)-[:HAS_MANDATE]->(m1:Mandate)-[:CHARGED_BY]->(merch:Merchant)
MATCH (u)-[:OWNS]->(acc2:Account)-[:HAS_MANDATE]->(m2:Mandate)-[:CHARGED_BY]->(merch)
WHERE acc1 <> acc2 OR m1 <> m2
RETURN merch.name AS DuplicateService,
       collect(DISTINCT acc1.bank + " (.." + acc1.last4 + ")") AS PayingAccounts,
       collect(DISTINCT m1.rail) AS RailsUsed,
       sum(m1.monthlyEstimate) * 12 AS AnnualWastedCapital

Query 4: Annualized Bleed Aggregation

Computes the total financial hemorrhage across all active and zombie mandates:

MATCH (u:User)-[:OWNS]->(:Account)-[:HAS_MANDATE]->(m:Mandate)
WHERE m.status = 'ACTIVE' OR m.status = 'ZOMBIE'
RETURN count(m) AS TotalActiveMandates,
       sum(m.monthlyEstimate) AS MonthlyTotal,
       sum(m.monthlyEstimate) * 12 AS AnnualBleedTotal

6. Cancellation Runbooks & Merchant Ghosting Protocols

The hackathon prompt explicitly mandates providing "the correct cancellation path for each mechanism, with the steps and what to do when the merchant does not respond."

Figure 3: Multi-Rail Cancellation Decision Tree & Ghosting Protocol Interactive Killswitch Navigation

The 4 Tailored Rail Execution Runbooks

  1. UPI Autopay Protocol (NPCI UMRN): Every UPI Autopay generates a unique Unique Mandate Reference Number (UMRN). Finatic extracts the UMRN directly from the SMS string. The app directs the user to open Google Pay / PhonePe $ ightarrow$ Profile $ ightarrow$ Autopay, locate the UMRN, and tap "Revoke". Re-authentication via UPI PIN permanently terminates the mandate at the NPCI switch level regardless of what the merchant attempts.
  2. Card Standing Instruction Protocol (RBI SIHub): Under RBI circular DPSS.CO.PD.No.750/02.14.003/2019-20, all card e-mandates must be manageable on an independent consumer portal. Finatic generates direct links to the user's specific issuing bank SIHub portal (e.g. HDFC SIHub, ICICI Card e-Mandates) where the user authenticates with an OTP and revokes the instruction directly, cutting off the merchant's ability to bill the card.
  3. e-NACH Netbanking Clearing Protocol: For gym memberships or loan EMIs registered via Netbanking, Finatic provides specific menu navigation steps for the top 5 Indian banks (HDFC, SBI, ICICI, Axis, Kotak) to place a stop-payment request on the mandate ID directly with the clearing bank.
  4. The Merchant Ghosting & Refusal Escalation: If a merchant deletes the cancel button, does not respond to support tickets, or bills anyway:
    • Step 1: Finatic generates a pre-formatted legal dispute letter quoting the UMRN / Mandate ID and Section 25 of the Payment and Settlement Systems Act.
    • Step 2: Steps to trigger an unauthorized recurring charge dispute / chargeback with the issuing bank.
    • Step 3: Escalation link to the Reserve Bank of India (RBI) CMS Portal (cms.rbi.org.in).
